Why Join?

A join is a way to say that two relations (tables) are connected, and to navigate from one to the other, usually through a foreign key (e.g. albums.artistId links to artists.artistId).

The slides' running example has two tables:

  • persons - each person's details (person_id, first_name, last_name, birth_date, street, town, county)
  • favourite_foods - who likes what (person_id, food)

Why multiple tables?

There are rules (normalisation) about how attributes are organised into tables, especially around the key that uniquely identifies rows. Benefits:

  • Less unintentional data redundancy (copies of the same data in several places cause problems when updating)
  • Less storage needed

The downside: some queries need data from more than one table. E.g. "list everyone who likes pizza" - SELECT person_id FROM favourite_foods WHERE food = 'Pizza'; only gives the ids, not their names.

Cartesian Product (CROSS JOIN)

The Cartesian product of sets S and T is the set of all pairs (s, t) with s from S and t from T. Its size is |S| × |T|.

cross_join.sql
SELECT *
FROM persons
CROSS JOIN favourite_foods;

Every row of persons gets paired with every row of favourite_foods (6 × 15 = 90 rows). Most of these rows are meaningless - the useful ones are where an attribute in one table matches an attribute in the other (e.g. both person_id values are 345678, i.e. Aoife's row paired with Aoife's foods).

The Join Operator

A join of R and S picks one attribute A from R and one attribute B from S. Each tuple r from R is compared with each tuple s from S, and when r's A value equals s's B value, they're combined into one tuple; otherwise no tuple is formed.

  • The result could be empty (no A value appears in the B column)
  • At most it's |R| × |S| (if every value matches)
  • Usually each row of R pairs with some, but not all, rows of S

Types of Join

  • (INNER) JOIN - only rows that have matching values in both tables
  • LEFT (OUTER) JOIN - all rows from the left table, plus the matching rows from the right
  • RIGHT (OUTER) JOIN - all rows from the right table, plus the matching rows from the left
  • FULL (OUTER) JOIN - all rows where there's a match in either table

Natural Join

Joins on the columns that have the same name (and compatible types) in both tables. No condition needed, and the duplicate column only appears once.

natural_join.sql
SELECT *
FROM persons
NATURAL JOIN favourite_foods;

Inner Join with ON

Usually you want more control, so you state the join condition explicitly:

inner_join.sql
SELECT first_name, last_name, food
FROM persons
INNER JOIN favourite_foods
    ON persons.person_id = favourite_foods.person_id
WHERE food = 'Pizza';

-- Aliases make it shorter to read
SELECT first_name, last_name, food
FROM persons AS p
INNER JOIN favourite_foods AS foods
    ON p.person_id = foods.person_id;

How to Think About a Join Query

For reasoning only (the database engine won't actually do it this way):

  1. Make the full Cartesian product C of the tables
  2. Keep only the rows of C that satisfy the ON condition
  3. Keep only the rows that satisfy the WHERE condition

Self Joins

A self join is a normal join where a table is joined with itself, using two aliases. E.g. list all pairs of people from the same county:

self_join.sql
SELECT p1.first_name, p1.last_name, 'and',
       p2.first_name, p2.last_name, 'both come from', p1.county
FROM persons AS p1
JOIN persons AS p2
    ON p1.county = p2.county
   AND p1.person_id < p2.person_id;

Without the last condition you get self-pairs (everyone paired with themselves) and every pair twice (A-B and B-A). Using < on the id keeps exactly one of each pair. Both ON and WHERE filter rows, but putting it in ON is arguably more readable.
