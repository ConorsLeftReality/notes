DML - Changing the Data

DML statements change what's in the tables. All three work on rows, and can hit multiple rows at once, so be careful

  • INSERT - add new rows
  • UPDATE - change values in existing rows
  • DELETE - remove rows
dml.sql
INSERT INTO students (id_number, first_name, last_name)
VALUES ('987654321', 'Graine', 'Gogerty');   -- missing columns become NULL (or their default)

UPDATE students
SET points = points + 10
WHERE hometown = 'Cork';

DELETE FROM students
WHERE hometown = 'Cork';
NOTE

No WHERE clause on an UPDATE or DELETE = it hits EVERY row. Always list the column names in an INSERT too, so it doesn't break if the table changes

NULL

NULL means the value is unknown or doesn't apply. You can't check it with =, use IS NULL / IS NOT NULL. Loads of NULLs can mean a badly designed database

DDL - Defining the Tables

DDL defines the structure: tables, indexes, views. The schema is the blueprint of the database

create_table.sql
CREATE TABLE students (
    id_number     CHAR(9),
    first_name    VARCHAR(20),
    last_name     VARCHAR(20),
    date_of_birth DATE,
    hometown      VARCHAR(20),
    course        CHAR(5),
    points        INT,
    PRIMARY KEY (id_number)
);
  • CHAR(n) - exactly n characters (shorter ones get padded)
  • VARCHAR(n) - up to n characters, good when you don't know the length (e.g. addresses)
  • SQLite doesn't really enforce types - it maps them to 5 "affinities" instead
